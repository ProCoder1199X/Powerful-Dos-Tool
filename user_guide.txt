## 🚀 Quick Start

### Basic Installation
```bash
# Clone repository
git clone https://github.com/yourusername/ethical-web-load-tester.git
cd ethical-web-load-tester

# Install (dependencies auto-install on first run)
python web_load_tester.py --help
```

### Your First Test
```bash
# Test your local development server
python web_load_tester.py \
  --target-url http://localhost:8080 \
  --users 20 \
  --duration 30 \
  --dry-run

# If dry-run passes, remove --dry-run to execute
```

## 📁 Configuration Files

### 1. Consent File (consent.json)
**Required for advanced attack modes**

```json
{
  "permission": true,
  "target_owner": "me",
  "target_domain": "mysite.com",
  "test_date": "2025-10-12",
  "test_purpose": "Performance and security testing",
  "authorized_by": "Your Name",
  "contact_email": "you@example.com",
  "max_duration_seconds": 3600,
  "allowed_attack_modes": ["flood", "slowloris", "burst", "adaptive"],
  "notes": "Testing staging environment before production deployment"
}
```

**Fields:**
- `permission`: Must be `true`
- `target_owner`: Must be `"me"` or `"authorized"`
- `target_domain`: Domain being tested
- `test_date`: ISO date of authorization
- `test_purpose`: Clear explanation of testing goals

## ⚔️ Attack Modes Explained

### 1. FLOOD Mode (Default)
**Purpose:** High-volume request flooding
**Use Case:** Test rate limiting, CDN capacity, load balancer distribution

```bash
python web_load_tester.py \
  --target-url http://localhost \
  --users 100 \
  --attack-mode flood \
  --duration 120
```

**Characteristics:**
- Maximum request throughput
- Minimal delays between requests
- Tests raw capacity
- Simulates sudden traffic spikes

**Metrics to Watch:**
- Response time degradation
- Error rate increase
- Server CPU/memory usage

---

### 2. SLOWLORIS Mode
**Purpose:** Resource exhaustion via slow connections
**Use Case:** Test connection timeout handling, max connection limits

```bash
python web_load_tester.py \
  --target-url http://localhost \
  --users 200 \
  --attack-mode slowloris \
  --duration 300 \
  --consent-file consent.json
```

**Characteristics:**
- Opens many connections
- Sends data very slowly
- Keeps connections alive
- Exhausts server connection pool

**Countermeasures to Verify:**
- Connection timeout enforcement
- Max connections per IP
- Request timeout limits
- Reverse proxy protection

---

### 3. BURST Mode
**Purpose:** Rapid traffic bursts
**Use Case:** Test cache behavior, burst handling, auto-scaling triggers

```bash
python web_load_tester.py \
  --target-url http://localhost \
  --users 150 \
  --attack-mode burst \
  --duration 180
```

**Characteristics:**
- 5-15 requests per burst
- Short pauses between bursts
- Simulates viral traffic patterns
- Tests spike capacity

**What to Monitor:**
- Auto-scaling response time
- Cache hit ratio changes
- Queue buildup
- Load balancer distribution

---

### 4. ADAPTIVE Mode (NEW!)
**Purpose:** ML-inspired intelligent load adjustment
**Use Case:** Realistic user behavior, find breaking points gradually

```bash
python web_load_tester.py \
  --target-url http://localhost \
  --users 100 \
  --attack-mode adaptive \
  --duration 600
```

**Characteristics:**
- Adjusts load based on response times
- Reduces pressure when server slows
- Increases load when server is healthy
- Most realistic human behavior

**Algorithm:**
- Response < 500ms → Increase load (0.1-0.5s delay)
- Response 500-2000ms → Normal load (1-3s delay)
- Response > 2000ms → Decrease load (2-5s delay)

**Best For:**
- Long-term stability testing
- Finding gradual degradation points
- Production-like traffic simulation

---

### 5. RUDY Mode (R-U-Dead-Yet)
**Purpose:** Slow POST body attacks
**Use Case:** Test POST timeout handling, upload limits

```bash
python web_load_tester.py \
  --target-url http://localhost/api/upload \
  --users 50 \
  --attack-mode rudy \
  --post-data "field=data" \
  --duration 240 \
  --consent-file consent.json
```

**Characteristics:**
- Sends POST data very slowly
- Large payloads sent in tiny chunks
- Ties up server processing
- Tests upload handling

**Defenses to Check:**
- Request body timeout
- Max upload size enforcement
- Chunked encoding limits
- Rate limiting on POST endpoints

  --users 100 \
  --use-tor \

**Privacy Layers:**

3. **MAC Spoofing**: Changes hardware identifier
4. **Identity Rotation**: Changes Tor circuit every 90s
5. **DNS Leak Prevention**: DNS through Tor (socks5h)

## 📊 Best Practices

### 1. Start Small, Scale Gradually
```bash
# Phase 1: Baseline (10 users)
python web_load_tester.py --target-url http://localhost --users 10 --duration 60

# Phase 2: Light load (50 users)
python web_load_tester.py --target-url http://localhost --users 50 --duration 120

# Phase 3: Moderate load (100 users)
python web_load_tester.py --target-url http://localhost --users 100 --duration 180

# Phase 4: Heavy load (200+ users)
python web_load_tester.py --target-url http://localhost --users 200 --duration 300
```

### 2. Monitor Server Resources
**During testing, watch:**
```bash
# CPU & Memory
htop

# Network connections
netstat -an | grep ESTABLISHED | wc -l

# Disk I/O
iostat -x 1

# Application logs
tail -f /var/log/nginx/access.log
```

### 3. Test in Isolated Environment First
```bash
# Use VMs or containers
docker run -d -p 8080:80 nginx
python web_load_tester.py --target-url http://localhost:8080 --users 100
```

### 4. Document Everything
```bash
# Create test log
echo "Test: $(date)" >> test_log.txt
echo "Purpose: Verify rate limiting" >> test_log.txt
echo "Command: python web_load_tester.py --target-url ..." >> test_log.txt

# Save results
cp ~/.ewlt_reports/report_*.json ./test_results/
```

## 🔧 Performance Tuning

### Optimize for High Load Testing

#### 1. System Limits (Linux)
```bash
# Increase file descriptors
ulimit -n 65535

# Add to /etc/security/limits.conf
* soft nofile 65535
* hard nofile 65535

# Increase network buffers
sudo sysctl -w net.core.rmem_max=134217728
sudo sysctl -w net.core.wmem_max=134217728
```

#### 2. Locust Performance
```bash
# Use multiple worker processes
python web_load_tester.py \
  --target-url http://localhost \
  --users 1000 \
  --workers 4  # 4 CPU cores
```

#### 3. Network Optimization
```bash
# Disable unnecessary services
sudo systemctl stop unnecessary-service

# Use wired connection
# Disable WiFi power management
sudo iwconfig wlan0 power off
```

## 🛠 Troubleshooting

### Issue 1: "Too many open files"
**Solution:**
```bash
ulimit -n 65535
# Or reduce --users parameter
```

### Issue 2: Tor bootstrap fails
**Solution:**
```bash
# Check Tor status
sudo systemctl status tor

# Restart Tor
sudo systemctl restart tor

# Check firewall
sudo ufw allow 9050
sudo ufw allow 9051

# Wait longer (up to 60s)
```

### Issue 3: High failure rate (>20%)
**Causes & Solutions:**
- **Server overwhelmed**: Reduce `--users` or `--spawn-rate`
- **Network issues**: Check connectivity, reduce load
- **Rate limiting active**: Good! Your defenses work
- **Firewall blocking**: Whitelist test IP

### Issue 4: MAC spoofing fails
**Solution:**
```bash
# Check interface name
ip link show  # Linux
ifconfig      # macOS

# Run with sudo
sudo python web_load_tester.py --mac-interface wlan0 ...

# Disable interface first
sudo ip link set wlan0 down
sudo python web_load_tester.py --mac-interface wlan0 ...
```

### Issue 5: DNS leaks detected
**Solution:**
```bash
# Ensure using socks5h (not socks5)
# Tool does this automatically with --use-tor

# Verify in logs:
grep "socks5h" ~/.ewlt_logs/ewlt_*.log

# Test manually:
curl --socks5-hostname localhost:9050 https://check.torproject.org/api/ip
```
